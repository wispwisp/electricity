# F06 Wiring Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The user turns on a Wire tool, picks a cross-section, and clicks terminal → terminal. Each wire gets the colour of its conductor, is routed automatically with right angles around the devices, and follows them when they move. Wires can be selected, deleted, re-sectioned and undone. A terminal takes two wires and a bar hole one. Edits that would leave a wire on a vanished terminal are refused. The supply block shows L, N, PE.

**Architecture:**
- `panelcore`: terminal roles and the supply's terminals become catalog data. `Project` gains wires (`w<n>` ids), terminal queries, the wiring rules and the colour rule. A GUI-free orthogonal router (`wirerouter`) computes polylines from obstacle rectangles and terminal points.
- App: undo commands for wires. `EditorScene` builds the router input from scene geometry on every model change and shows one `WireItem` per wire. It runs the wire tool: hover highlight, preview line, click-click, refusals. Designations move to their own items above the wires. `MainWindow` adds the Wire action and the section drop-down. `PropertiesPanel` shows a selected wire.
- Same rules as F05: commands call model methods and never touch items, and callers check validity before pushing.

**Tech Stack:** C++20, Qt 6.12.0 static (Core, Widgets, Svg; `QUndoStack` from Gui), Qt Test (core and offscreen GUI), Xvfb + xdotool for the smoke run.

**Spec:** `docs/superpowers/specs/2026-11-22-f06-wiring-design.md`

## Global Constraints

- No new Qt modules or plugins. Pictures and icons are rendered with `QSvgRenderer` (`svgIcon`, `svgRenderer`).
- Scene units are picture units, and the enclosure item sits at scene (0, 0). The supply's bottom stays 12 above the enclosure top: `tst_canvas` checks this.
- Wire sections in mm²: `1.5, 2.5, 4, 6, 10, 16` (`WireSections`). The toolbar default is `2.5`.
- Capacity: a device or supply terminal holds 2 wires, and an N or PE bar hole holds 1.
- Terminal ids are `"<object-id>:<terminal>"`.
  - Object ids: `supply`, `nbar`, `pebar`, and the device ids `d<n>`.
  - Bar holes are numbered from `1`, left to right: `nbar:1` … `nbar:8`.
  - Supply terminals are `supply:L`, `supply:N`, `supply:PE`.
- Wire ids are `w<n>`, from a counter that only grows. Undo restores a deleted wire under its old id.

## Review Focus

- **Undo removes the device a wire in progress started from:** the wire in progress is cancelled, the preview disappears, and the next click starts a new wire with no crash. Task 6 `undoCancelsWireFromRemovedTerminal`.
- **A selected wire while anything else changes** (a device moved through the model, a section changed): the wire stays selected and the properties panel keeps showing it, because wire items are reused by id. Task 5 `wireSelectionSurvivesResync`.
- **Growing or shrinking the enclosure with wires on the bars:** the bars move, and the wires end on the bar holes' new positions. Task 5 `wiresFollowEnclosureResize`.
- **A wire joining the top and bottom terminal of the same device (a bypass):** it is routed around that device, not across it. Task 3 `routesAroundOwnObstacle`.
- **Switching the language with a non-default section chosen:** the toolbar entries are rebuilt in the new language and the chosen section stays chosen. Task 6 `sectionChoiceSurvivesLanguageSwitch`.

  - `removeDevice` also removes every wire with an end on that device, then emits a single `changed()`.
  - `updateDevice` refuses when `orphanedTerminals(device)` isn't empty.
  - `fitsEnclosure` is false when `keepsBarWires` is false. The existing device rule stays.
  - Every successful wire mutation emits one `changed()`. A refused one changes nothing and emits nothing.
- The supply object id `supply` and the bar object ids `nbar`, `pebar` are fixed strings in `project.cpp`. Bar hole names are `1`…`nBarTerminals` (and `peBarTerminals`) of the current enclosure.

### Task 3: Orthogonal wire router (core)

**Files:**
- Create: `src/core/wirerouter.h`, `src/core/wirerouter.cpp`, `tests/core/tst_wirerouter.cpp`
- Modify: `src/core/CMakeLists.txt`, `tests/CMakeLists.txt` (`add_core_test(tst_wirerouter core/tst_wirerouter.cpp)`)

**Interfaces:**
- Produces, `wirerouter.h`:

```cpp
enum class Exit : std::uint8_t { Up, Down };

struct RouteEnd
{
    QPointF point; // the terminal
    Exit exit;     // the side the wire leaves its own obstacle from
};

struct RouteRequest
{
    RouteEnd from;
    RouteEnd to;
};

// One polyline per request, in request order. Each starts at from.point, ends at to.point and
// has only horizontal and vertical segments. Earlier requests claim their lanes first, so the
// same input always gives the same routes. Steps outside `preferred` (the enclosure interior)
// cost more.
QList<QPolygonF> routeWires(const QList<QRectF> &obstacles, const QRectF &preferred,
                            const QList<RouteRequest> &requests);
```

- Algorithm (in `wirerouter.cpp`; constants in an anonymous namespace):
  - **Grid.** Pitch `4.5`, so wires are 4.5 apart. Vertical lines at `x0 + i·4.5`, where `x0 = fmod(requests[0].from.point.x(), 4.5)`. Every terminal in the current art then lies on a line. Horizontal lines at `j·4.5`. Bounds: the union of all obstacles and route points, padded by 10 pitches.
  - **Blocked nodes.** A node is blocked if it lies strictly inside an obstacle grown by the clearance `1.5`.
  - **End nodes.**
    - Take the grid line nearest to `point.x()`.
    - From `point`, step rows in the exit direction until the first unblocked node.
    - The polyline begins `point → (point.x(), node.y()) → node`. The middle point appears only if `point.x()` is off the line, and is then a short jog.
    - If no free node is found within the bounds, use the fallback.
  - **Search.** A* over states (node, axis of arrival: horizontal or vertical). The start state's axis is vertical.
    - Step cost: `4.5`, ×3 when the node is outside `preferred`.
    - Bend (axis change): `+3·4.5`.
    - Entering a node that an earlier route used along the same axis: `+40·4.5`.
    - Bending at a node that an earlier route used: `+40·4.5`.
    - Going straight through a node an earlier route used across: `+4.5`.
    - Usage penalties don't apply at the route's own two end nodes.
    - Heuristic: Manhattan distance.
    - Ties: equal f costs pop in insertion order (keep a counter in the queue key), so results are deterministic.
  - **After a route.** Mark each node it passes with the axis of travel. A bend node gets both axes.
  - **Fallback** (no path): `{from.point, QPointF(from.point.x(), to.point.y()), to.point}`.
  - **Output.** Drop repeated points and merge collinear runs.
