# F02 — CI for Linux and Windows, local Linux executable script

Date: 2026-11-19 · Status: approved by the owner

Roadmap item: [F02](../../roadmap.md#f02-ci-for-linux-and-windows).
ADRs: [0003](../../adr/0003-toolchain.md), [0004](../../adr/0004-dependencies.md),
[0018](../../adr/0018-testing-and-quality-gates.md),
[0019](../../adr/0019-build-ci-distribution.md).

## Intent

Every push builds and tests the app on Linux and Windows and produces both
single-file binaries. Windows code has never been compiled, so this is the
first point where Windows problems can show up (0019, Consequences). The
owner also wants a local script that produces the Linux standalone
executable without going through CI.

## Goals

- `.github/workflows/ci.yml`: on every push and on manual dispatch, two jobs,
  `ubuntu-24.04` and `windows-2022`. Each job:
  1. restores a cached static Qt 6.12.0, or builds it from the official
     source archive and saves the cache immediately, so a later failing step
     does not discard the 1–2 h build;
  2. builds the app with the `release` preset;
  3. runs the full CTest suite (GUI tests offscreen);
  4. checks the binary's dependencies, failing on any Qt library or C/C++
     runtime that should be static: `dumpbin /dependents` on Windows (only
     system DLLs, no `vcruntime*`/`msvcp*`/`ucrtbase`/`api-ms-win-crt-*`),
     `ldd` on Linux (no `libQt6*`, `libstdc++`, `libgcc_s`);
  5. uploads the binary (`electricity-linux-x86_64`,
     `electricity-windows-x86_64.exe`) and the GUI test screenshots as
     artifacts.
  The Linux job also runs `scripts/quality_gates.sh`.
- **Local Linux executable script** (owner's request),
  `scripts/build_linux_executable.sh`: configures and builds the `release`
  preset, runs the Linux dependency check, and copies the result to
  `dist/electricity-linux-x86_64`. The CI Linux job builds its binary with
  this same script, so the local and CI files are made the same way.
  "Standalone" means what 0019 defines: Qt, its bundled libraries and the
  C++ runtime are inside the binary; glibc (2.38+), X11/xcb, GL, fontconfig
  and freetype come from the system. The script prints the libraries the
  binary still needs from the system.
- `quality_gates.sh` checks all files with clang-tidy when run in CI. It
  currently checks only files changed against `main`, which is nothing on a
  push to `main`.
- A CTest test fails if the Qt version pinned in the workflow differs from
  `cmake/QtVersion.cmake`.
- The Linux dependency check is covered by a test that proves it rejects a
  binary linking the C++ runtime dynamically.
- A new ADR records the CI-specific decisions below; roadmap F02 lists the
  script.

## Non-goals

- Release on tags, application icon, Windows version resource (F18).
- MinGW build job (0003 says CI may check it later).
- Pushing to GitHub: the owner pushes and pastes CI results back.

## Constraints

- Qt 6.12 supports only MSVC 2022 on Windows x86_64. `windows-2022` is still
  available and not marked deprecated (checked 2026-11-19), but it is the
  oldest Windows image. The `windows-2025` image ships Visual Studio 2026
  together with the MSVC 2022 toolset (14.44), which is the fallback when
  `windows-2022` is retired.
- clang-format in CI must be version 18, matching the container, because
  formatting output differs between versions.
- GitHub evicts caches unused for 7 days and scopes them per branch; the
  default branch's cache is readable from other branches. The first CI run
  should be on `main`.
- The session cannot see GitHub (no `gh`, no credentials). Windows-only
  failures are fixed from logs the owner pastes back.

## Approaches

There is one sensible way. 0019 fixes the shape: GitHub Actions, a native
Windows runner with MSVC, Qt built from source and cached. Prebuilt Qt
(official installer, aqtinstall) is not static. Building inside the dev
container image in CI was not considered further: the container definition
is outside this project's scope (CLAUDE.md), and 0019 names plain runners.
For the local script, the only question was whether CI should duplicate its
steps or call it; calling it keeps one recipe.

## Decisions (builder's calls)

- **Qt modules in CI:** qtbase, qtsvg and qttools only, skipping the
  optional modules the container's build pulled in (qtdeclarative,
  qtshadertools, qtlanguageserver, qtimageformats, qtactiveqt). This
  shortens the uncached build. It refines 0004's "same submodules" for CI
  and goes in the new ADR. The configure flags are otherwise those of 0004
  (Windows adds `-static-runtime`).
- **Cache key:** Qt version, OS, and a hash of the Qt build script, so a
  changed configure line rebuilds Qt.
- **Qt build steps live in a script** called by both jobs where the shell
  allows (bash on Linux, PowerShell or cmd on Windows), not inline YAML.
- **Source integrity:** the workflow pins the SHA-256 of each downloaded Qt
  archive.
- **No third-party actions** beyond `actions/*`; the MSVC environment comes
  from `vcvars64.bat` found with `vswhere`.
- **The binary is not stripped:** stripping saves about 13 % (30 MB →
  26 MB) and loses function names in crash reports.
- **Output folder** `dist/`, git-ignored.
- **Artifact retention:** 30 days.

## Done when

- Workflow, scripts and tests in place; the full local suite and
  `quality_gates.sh` are green.
- Locally verified: `scripts/build_linux_executable.sh` produces
  `dist/electricity-linux-x86_64`; its dependency check passes; the Xvfb
  smoke screenshot of that file shows the dark window; the workflow file
  passes a linter.
- Both CI jobs are green on the owner's push; the Windows artifact passes the
  `dumpbin` check; the Windows GUI screenshots have been inspected (the
  owner downloads them into the workspace).
- F02 marked ☑ in the roadmap.
